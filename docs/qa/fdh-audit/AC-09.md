# FDH v1.0 central audit ledger

[KAN-128](https://floorp-projects.atlassian.net/browse/KAN-128) requires
important operations to be auditable. D-20 moves audit records from PR and CI
attachments to a central append-only store after actor authentication. The
ledger stores structured audit records. GitHub and CI remain the sources for
review receipts, QA verdicts, approval, and evidence artifacts.
[AC-09 and FR-08](https://floorp-projects.atlassian.net/wiki/spaces/FI/pages/7471106/FDH+v1.0)
·
[Decision D-20](https://floorp-projects.atlassian.net/wiki/spaces/FI/pages/8061015/FDH)

## Run one ledger

1. Use a dedicated service account and a private durable directory for the
   database. The example uses `_dist/fdh/audit`; put it on a persistent volume
   if the worktree is disposable. Supply a random 32-byte lowercase hex key
   through the secret manager as `FDH_AUDIT_HMAC_KEY`. Keep it separately from
   the database and backups. Every verification of this ledger needs the same
   key.
2. Configure the existing Keycloak Workspace broker from the
   [AC-05 live spike](../fdh-workspace-oauth/LIVE-MCP-PROBE-2026-11-21.md). Keep
   the hardened Google provider and profile, including the `identity_provider`
   user-session-note mapping and fresh `@floorp.app` sessions after hardening.
   Configure an audit OAuth client to mint short-lived RS256 bearer access
   tokens with audience exactly `FDH_AUDIT_RESOURCE` and scope
   `fdh:audit:write`. The URL uses HTTPS and ends in `/v1/events`. The existing
   MCP probe scope and audience are separate. Provision a confidential reader
   client using client-secret Basic auth, client credentials, the `kc-admin-api`
   audience, and Keycloak's `view-users`, `view-realm`, and
   `view-identity-providers` roles. Enable introspection of the audit resource
   tokens by this reader as in the AC-05 setup. Supply `FDH_AUDIT_ISSUER`,
   `FDH_AUDIT_GOOGLE_CLIENT_ID`, `FDH_AUDIT_READER_CLIENT_ID`, and
   `FDH_AUDIT_READER_CLIENT_SECRET` to the service. On every POST, the service
   verifies the JWT and checks the active session and Google's federated subject
   through the broker.
3. Create the ledger once and retain its checkpoint independently of the SQLite
   file. Start the server behind the internal HTTPS reverse proxy. The listener
   binds to `127.0.0.1` on port 18884 by default. Set `FDH_AUDIT_PORT` to
   override it. Configure the proxy's request rate, body size and read deadline
   limits, and keep authorization headers out of proxy logs. Alert on 503 and
   507 responses. The row limit defaults to 100,000 and can be set with
   `FDH_AUDIT_MAX_ENTRIES` up to 1,000,000. Refusals consume ledger capacity.
   Give the proxy a rate limit sized for that capacity.

```sh
mkdir -m 700 -p _dist/fdh/audit
deno task fdh audit init _dist/fdh/audit/ledger.sqlite3 > "$AUDIT_CHECKPOINT"
deno task fdh audit serve _dist/fdh/audit/ledger.sqlite3 "$AUDIT_CHECKPOINT"
```

`init` refuses an existing database. `serve` verifies the chain against the
checkpoint before listening and refuses a missing ledger, a wrong key,
modification, or a ledger that lacks the pinned checkpoint.

## Record and trace an operation

Set `FDH_AUDIT_RESOURCE` and supply a fresh access token through
`FDH_AUDIT_ACCESS_TOKEN` in the client's environment. Use one UUIDv4 trace ID
across related records and a different UUIDv4 event ID for each record. The same
event from the same Workspace actor can be retried with the same ID. A different
payload or actor using that ID receives a conflict.

```json
{
  "id": "a56b0118-aa15-4038-81fc-c9d168098615",
  "traceId": "a25bbcb5-e961-4af0-91db-7390fbec03a2",
  "operation": "review",
  "target": {
    "kind": "pull-request",
    "repo": "Floorp",
    "pr": 123,
    "head": "0123456789abcdef0123456789abcdef01234567"
  },
  "agentRunId": "e302ae02-a6a3-4ebe-bd1e-a8c69f4272ed",
  "toolRunId": "3ad84df7-e090-4873-ade0-0f1a711e4881",
  "outcome": {
    "kind": "receipt",
    "reviewVerdict": "approve",
    "artifactSha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
  }
}
```

```sh
deno task fdh audit append "$AUDIT_EVENT_JSON"
deno task fdh audit trace _dist/fdh/audit/ledger.sqlite3 \
  a25bbcb5-e961-4af0-91db-7390fbec03a2 "$AUDIT_CHECKPOINT"
```

For external changes, append an `intent` before the separately authorized
operation. Proceed only after receiving a committed checkpoint. After the
operation, append a `result` using a new ID, the original intent's ID as
`intentId`, and status `succeeded`, `failed`, or `denied`. The result must match
the actor, trace, operation, and target of the intent. A result can also include
an artifact digest. If the result write fails, retry that event; reconcile an
uncertain external outcome before taking further action. GitHub approval and
release gates still decide whether the underlying operation may run.

The supported operations are `review`, `evidence`, `qa`, `github-change`,
`jira-change`, and `release`. Targets use a Floorp or Floorp-Runtime PR or CI
run and its full head SHA, or a KAN issue key for Jira changes. Receipts store a
SHA-256 of the original artifact bytes and the declared verdict for review
receipts. Recover the corresponding artifact from the PR or CI and verify its
bytes against the digest. Only references, the verified Google subject and
server-generated metadata are persisted. The optional agent, tool, and runner
UUIDs are caller-supplied correlation IDs. Credential strings, email addresses,
URLs, filenames, notes and raw artifact content have no fields in the API.

Authentication and validation refusals at the write endpoint are recorded with a
fixed reason. The ledger records the actor if authentication succeeded.
Uncommitted writes get a fixed error response and a server diagnostic without
request data. Database administration and trace reads are offline operator
commands. The HTTP service only accepts audit appends and offers no replace,
delete, or read endpoint.

## Back up and verify

```sh
deno task fdh audit backup _dist/fdh/audit/ledger.sqlite3 "$AUDIT_BACKUP_DB" \
  > "$AUDIT_BACKUP_CHECKPOINT"
deno task fdh audit verify "$AUDIT_BACKUP_DB" "$AUDIT_BACKUP_CHECKPOINT"
```

Use a new destination for each snapshot. Store snapshot checkpoints
independently of the database. Stop the service before restoring, verify a
snapshot against the last checkpoint the recovery must preserve, and start from
that verified copy with the expected checkpoint. A backup older than that
checkpoint will be rejected. Keep the existing database for investigation if
verification fails.

SQLite commits each append transaction before acknowledging. SQLite triggers
refuse row replacement, mutation and deletion. The store verifies an
HMAC-SHA-256 chain on open and during offline inspection. A filesystem
administrator can replace files. Against a replaced or truncated database,
verification relies on a recent independently retained checkpoint. A
genesis-only checkpoint cannot detect valid-tail deletion. A party with both the
ledger key and control of the independent checkpoints can forge history.

## Verification and coverage

The Linux host suite passed 2,252 tests with four existing skips, and repository
lint passed. A loopback CLI smoke run initialized and served the ledger,
recorded an HTTP 401 refusal, and verified the running ledger and its online
backup at the same checkpoint.

| Scenario                             | Evidence                                                                                                                                                                                                        |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace identity and authorization | Host test uses a real signed RS256 fixture and simulated Keycloak HTTPS endpoints. It verifies the federated Google subject, wrong audience, wrong scope, expiry, and immediate rejection of inactive sessions. |
| Important operation trace            | Host test reopens the ledger and traces a review intent, receipt and denied result with agent, tool and runner references. It also verifies same-event replay, owner binding, and duplicate-result rejection.   |
| Persistence failure and full ledger  | Host test injects a SQLite write abort and exhausts the configured row limit. Neither rejected write advances the ledger. A committed event can still be replayed at capacity.                                  |
| Original-record mutation and restore | Host test rejects SQL update, delete and replace, detects direct tampering on verification, restores a backup, and rejects an older snapshot against a newer checkpoint.                                        |
| Secret exposure                      | Host test sends rejected fields and tokens and checks that they are absent from stored rows, including denial rows. The write-abort response omits the injected SQLite diagnostic.                              |

The implementation has an explicit audit submission path. Existing local FDH
commands can operate offline and direct changes via GitHub or Jira can still
bypass FDH. A deployment needs operator wiring for those important operations,
separate runner-machine identity if runners submit as principals, and a
shared-environment verification with real audit-scoped Workspace tokens. The
recorded AC-05 live run used the MCP probe resource.
