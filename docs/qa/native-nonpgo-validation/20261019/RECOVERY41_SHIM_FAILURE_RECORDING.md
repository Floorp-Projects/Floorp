# Shim failure recording

The daily Intel `connected` timeout did not preserve enough information to distinguish a child exit, rejected hello, host timer, missing observer delivery or a cleanup-induced error. The host answered a state request after the timeout, so browser death was not established. This change records observations before cleanup and does not claim to repair native authentication.

Both daily QA entrypoints now use `shim_failure_diagnostics.py`. An independent app-scoped observer retains the first event, first disconnect, total count and most recent 16 allowlisted events. It leaves the functional event arrays intact. Before any service-stop, Marionette-close or host-close request, it records separate browser/launcher state, the child monitor snapshot, functional failure and observer history. Missing events or undiscovered child identity remain unknown.

`native-before-cleanup.json` is written exclusively with mode 0600 and fsync before cleanup begins. Cleanup operations are attempted independently and recorded in a bounded list; the first cleanup failure is retained separately from the functional failure and reported native cause. A separate `native-after-cleanup.json` records resulting process state and requested signals. An unavailable browser RPC, failed persistence or cleanup failure is recorded without suppressing independent host/monitor collection or subsequent cleanup. Observation timestamps are not kernel event timestamps; a reported native cause is not automatically the underlying root cause.

The public `project_diagnostics()` reprojects a fixed schema. It excludes PIDs, argv, private paths, app IDs, nonces, arbitrary reasons and exception text. `native_suite.py` retains the projected context/GUI records independently of its existing first-cause and legacy failure snapshots. The controlled `native_cause.py` path retains its earlier diagnostics and is not given the new observer hooks in this change.

The pinned QA harness remains `cbe45a7d7480d713b2c40a9ed348420126e6ccb0`. A separate bound recording patch applies after the existing startup patch. It preserves the complete HostProcess class, native process inventory and ownership rules, and the context harness's existing iteration counts, pre-cleanup evidence, first-failure persistence, private streams and lifecycle results. The context harness reuses its existing child monitor. The plan verifies patch, base, result and helper hashes; prepared-harness preflight verifies the final files as well.

Short controls cover authentication timeout followed by several cleanup failures, early startup failure, unavailable RPC and process observations, bounded event overflow, first-versus-recent cause retention, actual JavaScript observer execution, privacy projection and pre/post persistence. Kernel event handling and browser/ Shim GUI authentication still require the subsequent native validation; mocks and the JavaScript control do not qualify them.
