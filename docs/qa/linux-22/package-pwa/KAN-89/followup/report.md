# KAN-89 focused official Flatpak / KDE X11 follow-up

Scope: actual official Flathub Floorp 12.21.1 / Gecko 159.0.1 on Debian 13 with a **new independent** Xvfb :90, runtime directory, HOME/profile and D-Bus session. This is KWin X11 6.3.6 + Plasma, not the reporter's Manjaro/KDE Plasma6.7.4 installation. Existing other QA desktops/profiles were not used. Plasma/QtQuick used its software rendering backend in this headless X11 session, as explicitly set in session_probe.py; this is not physical GPU/display qualification. Product rendering/security preferences were not changed. Assigned Floorp source remains `984509d2053be7bae9027133bda7259cd706b208`. No product bytes, signature policy, content sandbox settings, experiment gates, KWin protocol permissions or identity rules were changed.

## Environment improvements and retained failures

Initial Xvfb crashed because the prefix EGL library loaded the host Mesa driver. Setting LIBGL_DRIVERS_PATH and the EGL vendor JSON to the **same installed dependency prefix** resolved it without disabling GLX or rendering validation. KWin then advertised a real supporting WM and _NET_WM_ICON support. ActivityManager, global accelerator, kded6 and Plasma were started in the independent normal session; the matching service names were observed on its bus. Alt+Tab was actually displayed. Missing prefix service executables still produce document/desktop/Flatpak portal activation warnings; they are retained as infrastructure limitations.

The official Flatpak exports directory was added to the desktop search path. The normal `XDG_MENU_PREFIX=plasma-` was required for kbuildsycoca to read the installed menu. The original export's `/usr/bin/flatpak` does not exist in this prefix environment. For the final contrast, a copy of the **existing official** `one.ablaze.floorp.desktop` was placed in the dedicated user's applications directory with only each Exec executable path relocated to the actual prefix Flatpak executable. All remaining lines and Exec arguments, including Icon=one.ablaze.floorp and StartupWMClass=floorp, are unchanged. `desktop-prefix-relocation.json` records hashes and checks. This is a prefix adaptation, not a product packaging patch or a forced KWin mapping.

A dedicated GTK icon theme contains known official Floorp and Firefox64px PNGs. A standalone GTK helper (never loaded into the product) measured the actual sandbox theme/search paths. This revealed that the host-side data directory initially did not expose the theme to the sandbox. Installing the same theme through ordinary file operations **inside the dedicated sandbox's actual XDG_DATA_HOME** corrected the condition: gtk-theme-probe.txt reports floorp sizes64 and firefox sizes64, while one.ablaze.floorp resolves normal app icons16..128. Early ineffective-theme runs are kept in named subdirectories and are not treated as a valid icon-theme comparison.

## Accurate actual-client identification

Each product uses the unique local fixture title `KAN89 <locale> dedicated`, an exact ProfD equality guard and executable `/app/lib/floorp/floorp`. Main client identification comes from KWin's root _NET_CLIENT_LIST, with _NET_CLIENT_LIST_STACKING retained. Every client is queried for WM_STATE, class, title and icon properties; the unique matching **Normal client** must have the fixture title. Its geometry matches the browser geometry. Full root trees and the client children/decoration-parent tree are saved, so a frame or application leader is not mistaken for the main client. Native nsIBaseWindow.nativeHandle was a GTK/native pointer, not an XID, and windowUtils.outerWindowID returned undefined; neither was used as an X11 ID.

With the effective known GTK theme, signed Japanese/Spanish language packs and KWin/Plasma X11:

- en-US effective legacy brand is Floorp; ja and es-CL effective legacy brand is Firefox. Language packs are active with signedState2.
- Actual main WM_CLASS remains Navigator/floorp. `_NET_WM_ICON` and `_NET_WM_PID` are absent on the validated actual client, rather than being read from a wrong frame/leader.
- The synthetic Alt+Tab popup is visibly present. The captured browser tile shows a generic X symbol rather than the reported Firefox logo. KWin's read-only window observation reports resourceClass floorp and empty desktopFileName, including after the final normal launcher and Exec-only prefix adaptation. Plasma's taskbar is a separate surface: in the final adapted session it shows the Floorp icon in all three locales, while the KWin Alt+Tab tile still uses the generic X symbol.
- Content sandbox level6 and absence of MOZ_DISABLE_CONTENT_SANDBOX are checked. Successful rows record normal product quit and exit0. Synthetic xdotool keydown/Tab/keyup is explicitly **not physical input**.

Known PNG references, direct property data and screenshot pixels are kept separate. An absent _NET_WM_ICON has no image pixels to compare to either PNG; it is never called a matching icon or a successful fix. `compare_switcher_pixels.py` produces fixed-region screenshot crops and explicit numerical reference-render comparisons. These are reproducible image measurements with scaling/background caveats, not a claim that a screenshot tile is byte-identical to an official PNG. The first Alt+Tab icon crops are exactly identical across the three locales (RGB SHA256 bf3a692967beb4e16bad826652f0c594b2a762662530ed9d84c961e0b588f956). The final taskbar32px crops differ from the known Floorp default32 rendered over the sampled background by only mean absolute channel difference 0.01595 (maximum1), consistent with the visually observed Floorp taskbar icon and alpha-compositing rounding. This is explicitly distinguished from the unchanged generic-X Alt+Tab icon. See taskbar-pixel-comparison.json.
