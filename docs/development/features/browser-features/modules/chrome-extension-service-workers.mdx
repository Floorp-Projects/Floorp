# Native Extension Service Workers

The native implementation is maintained in
`.github/patches/floorp-runtime/common/chrome-extension-workers.patch`, against
Runtime 158 source `7dd619742b25567e479eeda97ae071d10542ad0b`.
It requires `--enable-extensions-webidl-bindings`; applying JavaScript patches
to an old binary cannot enable compiled Worker bindings.

The candidate's WebIDL parser and C++ binding generator checks pass. Native
classes and generated bindings are checked against the candidate's actual
headers. A complete Runtime 158 developer build starts actual classic and
module background Workers with the global experimental policy disabled; its
internal script-cache regression and sixteen public messaging cases also pass.
Developer tests also verify native context records, actual stop/event/restart,
headed optional-management grant and revocation, and cached API lifetime across
actual Worker garbage collection. The complete SDK regression suite passes on
the Linux developer build, including native speech callbacks
and event wake-up after termination. Production package gates remain under
verification.
Developer runs do not qualify a production package. Historical Firefox 157
document fallback results do not qualify this implementation.

## Selection and loading

The ordinary `extensions.backgroundServiceWorker.enabled` default stays false.
A separate immutable per-extension policy selects native execution only for a
valid Chrome compatibility marker with matching original/installed IDs, and
only when WebIDL bindings were compiled. Registration, script loading and API
exposure use that policy. Ordinary Firefox extensions retain upstream selection;
the existing experimental preference still supports upstream tests. The native
internal script cache also checks the target URL's current thread-safe extension
policy instead of requiring that global preference. This allowance is confined
to the privileged internal cache namespace; public Cache API scheme validation
keeps its existing behavior.
The process conduit actor is registered on compiled Worker builds independently
of the global experimental preference. Actual Worker creation and every conduit
request still pass their extension policy and context checks.

The converter reads the actual `AppConstants.MOZ_WEBEXT_WEBIDL_ENABLED` flag.
It does not use the globally disabled experimental Worker preference as a
capability test. On compiled candidates it preserves the original service
worker path and classic/module type. On older binaries it uses the explicit
document fallback and records the selected mode and warning in diagnostics.
An existing cross-browser document background retains its intended precedence.

The manifest's type reaches `ServiceWorkerManager` as `WorkerType::Classic`
or `WorkerType::Module`. Classic workers retain `importScripts`; module workers
use static ESM imports. The existing Service Worker restrictions on dynamic
`import()` and module `importScripts()` remain intact.

Compatible extension pages also receive access to their genuine native
`navigator.serviceWorker` registration/container. This is needed by packages
which wait for `ready` or inspect `getRegistration()`. It uses the same native
policy gate rather than enabling extension Service Workers globally.

## Native API bindings

Bindings dispatch through the existing extension child/parent implementations,
including schema validation, permission checks and target-document checks.
The patch adds storage, tabs, action, DNR, Offscreen, Side Panel, userScripts,
debugger, identity, notifications, tabGroups, permissions, cookies, webRequest,
management, privacy, contextMenus, downloads, webNavigation, tabCapture,
desktopCapture, fontSettings, TTS, bookmarks, commands, history, i18n, idle,
sessions, topSites, omnibox, Power and extension access checks, in addition to
upstream namespaces and `runtime.getContexts`.

New bindings have WebIDL definitions, build-list entries, generated binding
configuration, native classes, Browser getters and cycle collection. An empty
namespace or generated NotImplemented success is not a backend implementation.
Schema enum properties use the actual schema enumeration and Chrome key naming.
Power.Level and tabCapture.TabCaptureState are installed directly by their native
wrappers as own writable, enumerable and configurable data properties. Deleting
them leaves no prototype accessor fallback; their values are retained after
permission revocation while method calls still require current authorization.
Worker-only API availability follows the Chrome reference: DOM-only extension
aliases such as getViews/getBackgroundPage/getURL are not invented in Workers.

The converted Worker root is a native JavaScript object. It retains normal
property descriptors, accessors and prototype operations while its resolve hook
installs genuine native SDK objects. Optional namespaces are initially absent;
a real permission grant exposes them on the same root and Worker generation.
After revocation the same namespace references remain visible, while every call
and event registration checks current namespace and member permissions. A fresh
Worker starts with only its current grants. Internal manifest-presence tokens
are kept out of the extension's public permission Set and `permissions.getAll`.
Ordinary Firefox extensions retain the original native DOM root.

MV3 Chrome `userScripts` also requires the per-extension **Allow user scripts**
switch in the Add-ons Manager permissions panel. Its private setting never
grants the public `userScripts` permission. Turning it off denies current and
captured API calls and suspends registered scripts in both USER_SCRIPT and MAIN
worlds, including pending injections. Registrations remain stored and resume
when permission and the setting are both enabled. Pages and Workers retain an
already observed SDK object, while an unread namespace stays hidden after
revocation. Ordinary Firefox and legacy MV2 user-script behavior is preserved.

Member visibility is sampled when a native namespace is first accessed, matching
the measured Chrome contract. Public namespaces such as `runtime` and
`management` omit permission-restricted methods when initialized without their
grants; existing namespace objects retain that shape after a later grant.
Captured permitted functions remain present after revocation, with live call
authorization denying further access. The generator keeps explicit measured
visibility exceptions for APIs whose callable surface remains available.

Root enumeration stays lazy: `Object.keys(chrome)` and `Reflect.ownKeys(chrome)`
list available namespace names without creating SDK objects or sampling member
permissions. An explicit namespace read or property descriptor materializes that
namespace, matching Chrome. The native enumeration hook preserves authored own
properties and their flags; sealing/freezing uses the engine's lazy-property
resolution before closing the object.

Native methods are own writable, enumerable and configurable data properties.
Their reserved-slot forwarders call the genuine compiled IDL function with its
original SDK receiver, so detached calls preserve the extension context. Only
matching generated native methods are mirrored; shared-prototype script,
callable Proxy, WebAssembly, builtin and accessor additions are ignored.

The native cached Chrome root participates in the engine's JavaScript holder
tracing. Its SDK objects, functions and authored properties survive collection
between asynchronous callbacks. A separate classic/module regression requires
an unreachable weak sentinel to be collected before verifying those identities
and genuine asynchronous storage operations.

Management results use original Chrome IDs for converted add-ons, including
disabled add-ons whose native installation metadata retains that identity.
`management.get` and `setEnabled` accept those IDs with the existing permission
and policy checks. Chrome uninstall events carry the ID string; ordinary Firefox
callers retain upstream IDs and event objects.


Special contracts are implemented where generic JSON dispatch is insufficient:

- `runtime.onMessage` uses a native handled/value response envelope. Ignored
  listeners settle without winning over another listener's response; synchronous
  `sendResponse`, returned Promises and asynchronous callbacks retain their
  distinct behavior. A native-listener-only witness hook handles the transport
  Promise without weakening ordinary message-response principal checks.
- Callable `scripting.executeScript` functions and JSON arguments are serialized
  on the Worker thread, then handled by the real injection backend.
- `contextMenus.create` returns its ID synchronously while completion and errors
  use its asynchronous callback. Desktop selection likewise returns a request
  ID immediately; cancellation suppresses its result callback.
- Identity promises preserve the result object, while legacy callbacks receive
  token and granted scopes. Native message/Port routing retains original IDs.
- Omnibox suggestions use per-context callback routing and validate every update;
  old-input callbacks expire. A callback may deliver multiple suggestion sets.
- TTS retains `options.onEvent` on the Worker thread and routes genuine engine
  events back to it. Terminal events, failure and shutdown release callbacks.
  Parent-side numeric checks reject invalid volume, pitch and nonfinite or
  excessive rates before changing speech state. These errors currently reject
  asynchronously; Chrome rejects them synchronously in its bindings.
- Synchronous i18n resolves the extension's actual locale catalog rather than
  depending on an unavailable synchronous parent request.
- `extension.setUpdateUrlData` validates one string of at most 1024 characters
  and returns synchronously. Chrome ignores this value for Web Store installs;
  Floorp's authenticated Store updater follows that contract. Custom Chrome
  update feeds are not enabled by this API. Ordinary Firefox API exposure is
  unchanged.
- WebRequest listeners forward filters/options and retain asynchronous auth
  callback results. Ordinary event listeners cannot supply privileged metadata.

## Gestures and lifetime

Native event gestures cross the Worker boundary only through trusted internal
listener/request metadata. RAII scopes the flag to the synchronous callback and
restores it afterward. Schema methods requiring a gesture reject requests made
outside that scope; extensions cannot assert their own gesture flag.

Idle termination preserves the registration and primes persistent listeners.
A subsequent real event starts the registered worker and delivers the event.
Startup watchers and activation listeners are removed on shutdown. Disable,
update and uninstall terminate old contexts and release pending calls, callbacks
and Ports; old extension generations cannot handle new events. Worker context
records use real proxy lifetimes and omit document fields. Context teardown
removes the old background view, and native termination returns its actual
completion Promise to the privileged caller.
A new background owner waits for that exact previous termination Promise before
registering startup watchers or waking a Worker. This prevents a stopped parent
state from starting a new incarnation while the old child context is unloading.
Native Promise reactions can forward cleanup requests without a JavaScript
caller stack. The main-thread request retains an undefined stack in that case;
it creates a saved-frame object only when deserialization returned an object.
`ChromeTtsValidationNative.test.mts` exercises this path with rejected speech
requests and event callbacks in actual document and Worker contexts.

## Execution gates

For native registration diagnosis, `MOZ_LOG=WorkerTelemetry:5` reports script
comparison, cache/fetch failure status, update failure and worker initialization
stages. This logging is off by default and adds no permission bypass or fallback;
the new failure records contain stage names and error codes rather than URLs or
extension data.

The production browser suite is:

```sh
python3 tools/chrome-extension-runtime/run-browser-tests.py \
  --browser /path/to/rebuilt/floorp \
  --candidate-manifest /path/to/native-runtime-manifest.json \
  --headed \
  --actor-module browser-features/modules/modules/chrome-web-store/test/helpers/UserScriptsConsentUIChild.sys.mjs \
  --test browser-features/modules/modules/chrome-web-store/test/workers/WorkerNative.test.mts
```

It requires actual Worker globals and covers both script types, storage,
function/file injection, callback/Promise/lastError behavior, native contexts,
permission failures and real event wake-up after termination. Tests also cover
tab/cookie/group/font changes, native speech callbacks, locale catalogs and
additional namespace contracts. Missing compiled bindings fail explicitly.
`WorkerMessagingNative.test.mts` separately checks sixteen public message cases
across classic and module Workers: returned Promises and rejections, synchronous
and asynchronous callbacks, ignored listeners, multiple listeners and late
callbacks. A sender timeout is a failure. Its expected results come from the
frozen Chrome reference rather than the native transport implementation.
`WorkerPermissionsNative.test.mts` requires a headed native candidate and uses
a real toolbar invocation and permission prompt. It checks optional grant,
revocation, retained references, ordinary root descriptors and a fresh Worker.
`WorkerMemberPermissionsNative.test.mts` separately tests lazy root enumeration
and descriptor materialization with actual optional-management consent. Its
execution and the other headed permission tests are mandatory production
candidate gates. A raw developer build may provide early API feedback, but
does not qualify a production package.
`NativeBackgroundSelection.test.mts` separately checks converter selection,
classic/module preservation, cross-browser background precedence and diagnostic
mode reporting; both suites are in the native candidate CI gate.

Upstream suites provide additional regression coverage:

```sh
./mach xpcshell-test --tag sw-webextensions \
  toolkit/components/extensions/test/xpcshell/test_ext_background_service_worker.js
./mach xpcshell-test --tag sw-webextensions \
  toolkit/components/extensions/test/xpcshell/test_ext_service_worker_messaging.js
./mach xpcshell-test toolkit/components/extensions/test/xpcshell/webidl-api/
```

Native qualification must include stop/event/restart delivery, persisted
registration after browser restart, and update/disable/uninstall during startup
or an API request. Ordinary Firefox extensions run in the same candidate as
negative controls. Authentic MV3 corpus packages must report the actual
`background_worker` context when native selection is expected; a document
fallback operation is recorded separately.

## Reproducible candidate builds

`prepare-native-source.py` prepares an isolated checkout from the locked source
and maintained patches. Its incremental mode refuses unexpected postimages and
preserves unchanged timestamps. The original sibling Runtime checkout remains
unmodified. Use an explicit owned mozconfig/object directory and compile the
binding option; changing a reported JavaScript flag is insufficient.

The candidate workflow builds the real Floorp overlay and packages Linux,
Windows and macOS artifacts. Its manifest binds source and Floorp commits,
patch/package hashes, platform, ABI/build identity and native binding flag.
Matching packages are extracted and executed on their target OS. See the
[compatibility runtime](./chrome-extension-runtime.mdx) for the integrated APIs,
management/update contract and frozen real-extension qualification rules.
